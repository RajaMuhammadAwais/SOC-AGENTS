# Autonomous Agents: Skills, Memory, Knowledge, and the Policy Engine

This document explains how SOC-AGENTS agents operate autonomously while remaining safe and auditable. It is grounded in both the implementation (`backend/app/agents/`, `backend/app/domain/agents/`, `backend/app/domain/policy/`) and the research that shaped the design.

## 1. Research basis

The autonomy model synthesizes four strands of published work. IBM's taxonomy of agent memory distinguishes short-term (session rolling buffer), semantic long-term (knowledge bases, RAG), episodic (structured records of past runs and outcomes), and procedural (skills executed automatically without re-reasoning) memory [1]. The CoALA survey's taxonomy informs our choice to implement procedural memory as a declarative skill registry and episodic memory as an embedded case log [2]. Research on the human-in-the-loop spectrum (Strata's 2026 guide; Elementum) establishes that oversight level is a property of the *decision*, not the agent, and that time-boxed decision lanes with fail-safe-deny are the operative control for autonomous workflows [3] [4]. Finally, the AgentWard lifecycle security architecture frames the threat model: agent failures propagate across initialization, input processing, memory, decision-making, and execution stages, and must be contained with defense in depth [5]. The failure statistics are sobering — CMU's study found autonomous agents fail multi-step tasks roughly 70% of the time in simulation without structured oversight, and MIT found 95% of enterprise generative-AI initiatives fail during evaluation — which is precisely why this platform treats autonomy as a governed policy problem rather than a capability to maximize.

## 2. Skills: procedural memory

A skill is a named, versioned capability an agent may execute: `query_threat_intel`, `enrich_ioc`, `assess_risk`, `recommend_block_ip`, and so on. Skills live in the `agent_skills` table with:

| Attribute | Meaning |
|---|---|
| `name` / `description` | Human-readable identity and purpose |
| `required_permissions` | Permission set the calling principal must hold |
| `risk_class` | `informational`, `low`, `elevated`, or `critical` |
| `execution_policy` | `allow`, `require_approval`, or `deny` |

Skills are typed so that agents compose them without re-deriving reasoning on every call, and so that the policy engine can reason about their blast radius statically.

## 3. Memory: episodic recall with pgvector

`MemoryService` (`backend/app/domain/agents/memory.py`) implements episodic memory as case-based reasoning. Agents store typed memories — `decision`, `action`, `outcome`, `lesson` — with titles and narratives; the title-plus-narrative is embedded with bge-m3 and stored in the `agent_memories` pgvector column. Recall queries embed the analyst's question and retrieve the five nearest memories (`cosine_distance`, tenant-scoped), returning a relevance score alongside the narrative. The design consequence is that an agent triaging "phishing with credential harvesting" today can read lessons from a similar campaign last month instead of starting cold.

## 4. Knowledge: grounded reasoning (RAG)

`KnowledgeService` (`backend/app/domain/agents/knowledge.py`) maintains tenant-scoped playbooks, runbooks, and MITRE guidance as `knowledge_documents`. Documents are chunked, embedded with bge-m3, and indexed into the `vector_chunks` table with an HNSW index. Retrieval goes through the standard `RetrievalService` hybrid contract (keyword + semantic), and answers are generated by `generate_rag_answer` with cited evidence — retrieval evidence, not model invention, is what an analyst sees. This is the primary mitigation against hallucination liability in autonomous reporting.

## 5. The autonomy policy engine

`app.domain.policy.autonomy.evaluate_autonomy` is the gate every proposed autonomous execution passes through. Inputs are the skill's risk class, its execution policy, the tenant's autonomy maturity level, and an optional detection confidence. Output is one of three decisions:

- **allow** — the skill executes autonomously; the action is audit-logged with its reason.
- **require_approval** — the request enters a human decision lane, time-boxed by risk class (informational 0 s, low 60 s, elevated 120 s, critical 300 s). Timeout means **deny** — a missed window is a refusal, never implicit approval.
- **deny** — autonomous execution is refused; an analyst must act manually.

Evaluation order is strict, so the outcome is deterministic and testable:

1. A skill-level `deny` always wins; `require_approval` always routes to a lane.
2. L0 (manual) and L1 (advisory) permit no autonomous execution regardless of risk class.
3. The skill's risk class must be inside the maturity level's allow-set (L2: informational; L3: informational + low; L4: informational + low + elevated; `critical` never executes autonomously).
4. A provided confidence below the confidence floor escalates to a human lane — uncertain detections never auto-execute.

This implements the full oversight spectrum in one governed system: **HITL** for anything `critical` or approval-policy; **HOTL** for elevated-risk actions under L4 maturity (agents act, analysts audit after the fact); **HOOTL** for informational and low-risk actions at L3/L4 (fully autonomous, fully logged).

## 6. Agent graphs

The LangGraph supervisor (`app/agents/supervisor.py`) routes work to specialists. Each specialist is an independent graph with persistent state (`app/agents/state.py`), so any agent can be upgraded, gated, or replaced without disturbing the others:

| Agent | Responsibility |
|---|---|
| Triage | Deduplicate, prioritize, and categorize alerts; reduce false positives |
| Investigation | Correlate logs, build attack timelines, identify initial access and lateral movement |
| Threat hunting | Search similar attacks, users, endpoints, and IPs to surface hidden campaigns |
| Risk scoring | Compute 0–1000 risk scores with confidence and explanation |
| Report generation | Executive summaries, technical reports, MITRE mapping, root-cause analysis |
| Response | Recommend or (when policy allows) execute containment actions |
| Threat intelligence | IOC enrichment, IP/domain/hash reputation, CVE and ATT&CK mapping |

## 7. Guardrails summary

Autonomy in SOC-AGENTS is bounded by five enforcement mechanisms, any of which can independently stop an unsafe action: tenant-scoped permission checks on every skill invocation; the deterministic policy engine (risk class × maturity level × confidence); time-boxed human lanes with fail-safe-deny; per-tenant rate limits via Redis; and a mandatory audit log recording every autonomous action with its policy decision and reason. Continuous improvement closes the loop: analyst dispositions (false-positive labels) feed back into skill tuning and the RAG corpus, so the system gets safer as analysts use it.
